# ODPT（公共交通オープンデータ）活用ナレッジ＆将来設計ガイド

本ドキュメントは、公共交通オープンデータ協議会（ODPT: Open Data Challenge for Public Transportation）のデータ活用に関する知見、初期実装の経緯と撤去理由、および将来Trainfoへ再導入・拡張する際の推奨アーキテクチャをまとめたナレッジです。

---

## 1. 歴史的経緯と初期実装の撤去理由

### 初期実装（東武東上線単一路線時代）
Trainfoのプロトタイプ初期、東武東上線専用アプリとして開発されていた際は、クライアントサイド（ブラウザ）から直接ODPT APIを叩いて東武鉄道の運行情報（`odpt:TrainInformation`）を取得するクライアント（`odptApi.ts`）を実装していました。

### 撤去に至った理由
1. **マルチ路線化との不整合**:
   - JR埼京線・川越線、JR武蔵野線、つくばエクスプレスなど複数社（JR東日本・首都圏新都市鉄道・東武鉄道）のマルチ路線マップへと進化した際、東武鉄道のみ外部APIから取得する構成はアーキテクチャのバランスを欠いていました。
2. **クライアント直接アクセスの限界**:
   - ODPT APIはAPIキー（コンシューマーキー）を必要とするため、フロントエンド（GitHub Pages配信）にキーを埋め込むかユーザーに入力させる必要があり、セキュリティおよびUX（導入ハードル）の課題がありました。
3. **シミュレータとしての自律性**:
   - Trainfoは「タイムトラベル」や「遅延シミュレーション（定刻 / +5分 / +15分 / ランダム遅延）」など、ユーザーが任意にダイヤを操作できるシミュレータ設計へ進化しました。運行情報バッジも、外部APIへの依存ではなくアプリ内のシミュレーション状態と連動する形が最も整合的です。

## 2. ODPTデータのリソース評価と活用可能性

Trainfoのような鉄道可視化・シミュレータアプリにおいて、ODPTから取得できる主要なデータリソースの有用性と活用案は以下の通りです。

| リソース種別 | 有用度 | 活用アイデア | 主な提供事業者・備考 |
| :--- | :---: | :--- | :--- |
| **`odpt:Train`**<br>(リアルタイム車両位置) | **★★★★★** | **「フライトレーダー型」リアルタイム在線追跡**<br>現実の営業列車が今どの駅間・駅ホームにいるか、実際の遅延秒数を地図上に反映。 | 東京メトロ、都営地下鉄、東急、京王、小田急など。<br>※更新間隔が30秒〜1分のため、Trainfoの軌道補間（`trackGeometry.ts`）とのハイブリッドが必須。 |
| **`odpt:StationFacility`**<br>(駅施設・構内・バリアフリー) | **★★★★☆** | **駅詳細パネルのリッチ化**<br>「エレベーター最寄り号車案内」「ホームドア設置有無」「車椅子対応ルート」「改札・出入口番号」の表示。 | 東京メトロ、都営地下鉄、JR東日本、私鉄各社。<br>※**静的マスタとしてビルド時に取り込めるため、APIキー不要で安全に実装可能**。 |
| **`odpt:TrainTimetable`**<br>(列車編成・車両マスタ) | **★★★★☆** | **直通列車の充当車両・編成表示**<br>埼京線直通における相鉄車（12000系）判定、東上線直通におけるメトロ車・東急車の判定、10両/8両の編成表示。 | 各社。<br>※運用・充当情報と連携することで、マップ上の列車アイコンや編成グラフィックをリアルに描き分け可能。 |
| **`odpt:TrainInformation`**<br>(複数社運行情報) | **★★★☆☆** | **首都圏インシデントマップ**<br>遅延・運転見合わせ区間の線路を赤色ブリンク表示、振替輸送ルートのハイライト。 | 首都圏各社。<br>※クライアント直接ではなく、BFF（バックエンド集約）でのキャッシュ配信が前提。 |

## 3. 将来導入時の推奨アーキテクチャ

ODPTを再度導入・活用する場合、以下の2つのアプローチが推奨されます。

### アプローチ A: 静的インジェスチョン（推奨・難易度低）
**対象**: 駅施設データ（`odpt:StationFacility`）、車両編成マスタ、出入口情報など更新頻度の低いデータ。

```text
[ODPT API] 
    │
    ▼ (ビルドスクリプト: scripts/ingestOdptFacilities.cjs)
[正規化JSON / stations.ts]
    │
    ▼ (Vite Build)
[静的Webアプリ (GitHub Pages)]
```

* **メリット**:
  - APIキーを公開リポジトリやブラウザに露出させる必要がない。
  - ランタイムのAPI障害や通信ラグが一切発生せず、高速・安定動作する。
  - GitHub Pagesの静的ホスティング構成をそのまま維持できる。

---

### アプローチ B: エッジBFF集約（リアルタイム在線追跡モード）
**対象**: リアルタイム車両位置（`odpt:Train`）、運行情報（`odpt:TrainInformation`）。

```text
[ブラウザ / Trainfo]
    │
    ▼ (GET /api/live-trains)
[Cloudflare Workers / Vercel Edge Functions] (BFF)
    │ ├── APIキー秘匿
    │ ├── 複数事業者（メトロ・都営・東急等）を並列フェッチ
    │ ├── 差分正規化 & 10秒キャッシュ (KV / Cache API)
    │ └── レートリミット制御
    ▼
[ODPT API (各社エンドポイント)]
```

* **設計ポイント**:
  1. **補間ハイブリッド**:
     ODPTの在線位置は離散的（「A駅〜B駅間」等）かつ遅延（ポーリングラグ）があるため、サーバーから受け取った駅間データをもとに、Trainfo側の物理エンジン（`trainSimulation.ts`）で滑らかに駅間を連続移動させる。
  2. **モード切り替え**:
     「ダイヤシミュレーション（全路線・タイムトラベル自由）」と「LIVE在線モード（対応路線のみ・実時間同期）」をUI上で明確に切り替えられるようにする。

## 4. 規約・ライセンス上の留意点

ODPTのデータを利用する際は、以下の利用規約・ガイドラインを遵守する必要があります。

1. **クレジット表記**:
   アプリケーション内の設定やフッター、モーダル等に、以下の指定文言を明記する。
   > 「本アプリケーションで利用している公共交通データは、公共交通オープンデータセンターにおいて提供されるものです。商用・非商用を問わず、利用者は公共交通事業者各社からの直接のサポートを受けることはできません。」
2. **キャッシュとアクセス頻度**:
   ODPTへの直接過剰リクエストを防ぐため、適切なTTL（運行情報は1〜2分、在線位置は15〜30秒程度）を設定し、キャッシュを徹底すること。
